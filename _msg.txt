A7 约定的那一条：生产目标警示
-----------------------------
新增 archive/ops-scripts/_prod_guard.py，并在 6 个会连数据库的脚本里调用。
行为按目标分档：

    本机回环 / sqlite  → 只打印警示，照常继续
    远程（*.rds.…）    → 要求显式确认（--yes 或 OPS_SCRIPT_CONFIRM=1），
                         否则以退出码 2 终止

**这是对 A7 的一处强化，已在 README 里标注**：A7 说的是「非阻塞警示」，
但纯打印的警示在这里近乎无用——脚本打印完下一行就开始执行 DDL，操作者看到时
事情已经发生。故**仅对远程目标**加确认，本地目标仍非阻塞。

一个必须守住的细节：DATABASE_URL 整串里含**明文口令**。防护模块打印前一律
脱敏（user:***@host）。这与 A8 记录的问题同源——那次是响应里夹带 .env 凭据，
这里是日志里夹带。

实测四种情形（直接调 guard()，不触发任何真实连接）：
    远程+无确认 → 退出码 2，输出不含口令原文  ✓
    远程+已确认 → 退出码 0                     ✓
    127.0.0.1   → 退出码 0（无摩擦）            ✓
    sqlite://   → 退出码 0（无摩擦）            ✓

顺带：归档后脚本仍可运行
------------------------
脚本移出仓库根后 sys.path[0] 变成归档目录，原本连 `import config` 都会失败。
_prod_guard 在导入时把仓库根挂上 sys.path，因此
`python archive/ops-scripts/db-maintenance/init_db.py` 仍可用。
这是有意的——这些是数据库维护工具，将来仍可能需要。

归档过程中核实并记录的两处事实
------------------------------
- fix_db_final.py 用的是 **MySQL 语法**（ALTER TABLE ... MODIFY COLUMN），
  而实际库是 SQL Server。它在归档**之前**就会报错。归档不修复它——
  它作为「曾按 MySQL 写、后迁到 SQL Server」的证据，原样才有意义。
- codemods/ 里那几个脚本**会原地改写 server.py**，它们正是 §3.5 那批注释污染
  的来源。保留它们有明确价值（是那批污染成因的唯一证据），README 中已写明
  「不要运行」。
