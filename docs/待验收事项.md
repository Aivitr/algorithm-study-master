## ☐ A1 · `database.py` 的 `connect_args` 改动（业务代码）

**时间**：2026-10-01 · **分支**：`test/local-db-baseline`（已并入 `main`）

**改了什么**

```python
# 改前 —— 无条件传入
connect_args={'timeout': 10, 'login_timeout': 10}

# 改后 —— 按方言选择
_IS_MSSQL = SQLALCHEMY_DATABASE_URL.startswith("mssql")
connect_args={'timeout': 10, 'login_timeout': 10} if _IS_MSSQL else {}
```

**为什么**：`login_timeout` 是 pymssql 专有参数。原先无条件传入，导致 `DATABASE_URL` 指向 sqlite 时 `sqlite3.connect()` 抛 `TypeError`，本地测试库无法建立。

**生产影响**：**无**。mssql 分支下传入的实参与改前逐字一致。

**验证**：`tests_safe/` 5 项测试通过。

**需要你决定**：是否接受这处对业务代码的改动。
> 若你认为应等到阶段 1 测试体系成型后再动 `database.py`，可以回退——本地库方案也可改用容器内 MSSQL 替代。

## ☐ A5 · 行尾符（LF/CRLF）风险

**时间**：2026-10-01

**事实**：本仓库文件为 LF，但 git 配置为检出时转 CRLF。每次提交都出现
`LF will be replaced by CRLF the next time Git touches it`。

**风险**：阶段 3 将大规模搬迁文件，届时**某次检出可能重写整个文件的行尾符**，使 diff 被无关变更淹没，也让「仅改物理位置、不改内容」这一承诺难以自证。

**建议处置**：阶段 3 开始前引入 `.gitattributes`（`* text=auto eol=lf`）。

**需要你决定**：是否同意引入 `.gitattributes`，以及时点。

## ☐ A7 · 两条路由绕过 ORM 直连生产库

**时间**：2026-10-01 · **位置**：`server.py:1935`（`/api/register`）、`server.py:1985`（`/api/login`）

**事实**：这两条路由**不使用 ORM**，而是直接

```python
import pymssql
conn = pymssql.connect(server=os.getenv("DB_HOST"), ...)   # 完全不读 DATABASE_URL
```

由此产生三个后果：

1. **隔离失效**：仅把 `DATABASE_URL` 指向本地库**对这两条路由毫无作用**——调用即连生产库并写入
2. **无法本地化**：`pymssql` 只讲 MSSQL，本地 sqlite 无法承接，**这两条路由无法在本地库上测试**
3. **配置双轨**：`.env` 同时维护 `DATABASE_URL` 与 `DB_*` 两套指向同一库的配置

同一模式还存在于 `init_db.py`、`check_all_tables.py`、`check_users.py`、`check_users_quick.py`（及 `test/` 下同名副本）——**运行这些脚本即对生产库执行操作**，其中 `init_db.py` 含建表语句。

**已做的防护**（未改动业务代码）：

- `tests_safe/conftest.py` 把 `DB_*` **显式赋成无害值**（不能删除——`config._load_dotenv` 用 `setdefault`，删了会被 `.env` 的生产值填回）
- 加 socket 层兜底：测试会话内阻断一切非回环连接，与具体实现无关
- 3 条回归断言钉死这两条路径

该盲区已在 `docs/route-inventory.md` 第四节中登记：它们无法纳入冒烟基线。

**需要你决定**：

1. 这两条路由是否**长期统一到 ORM**？这是根治办法，但属于改变业务代码，我未擅自实施
2. 若不改，是否接受它们**永久排除在自动化测试之外**——冒烟基线会留有这两处盲区
3. `check_*.py` / `init_db.py` 这几支脚本，是否需要在归档时加显著标注以防误跑

## ☐ A8 · 测试隔离只挡网络，挡不住「把凭据读出来写进响应」

**时间**：2026-10-01 · **位置**：`tests_safe/conftest.py`

**事实**：`conftest.py` 的三层隔离挡住的是**网络出口**。但处理器仍能自由读取 `.env`，
把里面的凭据放进响应体——而基线响应会被写进随仓库提交的 `tests_safe/baselines/routes.json`。

本次就撞上了：`/api/agora-token` 的响应取自 `.env` 的 `AGORA_*`。本机恰好缺
`AGORA_APP_CERTIFICATE`，它才没有生成真实 Token、才显得"可复现"；**换一台配齐凭据的
机器录制，基线文件里就会落进一个带时效的真实 Token**。该路由已排除。

**已做的防护**（未改动业务代码）：

- 新增 `test_responses_do_not_leak_env_secrets`：从 `.env` 取出 10 个疑似凭据值
  （`*_KEY` / `*_SECRET` / `*_TOKEN` / `*_PASSWORD` / `*CERT*`，长度 ≥ 8），
  逐条断言不出现在任何基线响应中。已用注入样本验证该断言确实会失败，非空转。

**需要你决定**：

我考虑过更彻底的做法——让 conftest 把 `AGORA_*` / `OSS_*` / `LLM_*` 也显式赋成无害值。
**没有做**，因为 `llm_service`、OSS 客户端等模块可能在导入期就需要这些值，一旦置空，
`import server` 可能直接失败，会让整套测试失去意义。

1. 维持现状（只加响应扫描这一道）——**我倾向这个**：成本低、不动运行时行为，且已能拦住
   同类路由被误加进基线
2. 或是我去逐个试验哪些凭据变量可以安全置空，能做的话再补上——工作量明显更大
