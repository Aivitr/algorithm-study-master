## ☑ A5 · 行尾符（LF/CRLF）风险 · **已决定：立即引入，已实测零影响**

> **决定（2026-10-01，授权范围内）**：引入 `.gitattributes`，**提前到阶段 1 执行**
> （原计划"阶段 3 开始前"）。
>
> **实测依据**：加入前执行 `git ls-files --eol`，索引中 **154 个文件全部为 LF、
> 0 个 CRLF**。因此固化现状**不产生任何重写 diff**——实测加入后索引中除
> `.gitattributes` 自身外无任何文件变化。
>
> **附带处置**：4 个 `.ps1` 脚本显式保留 `eol=crlf`（Windows PowerShell 对 LF
> 脚本的处理存在边界情况，且它们不是重构对象，不应顺带改变行为）。

**时间**：2026-10-01

**事实**：本仓库文件为 LF，但 git 配置为检出时转 CRLF。每次提交都出现
`LF will be replaced by CRLF the next time Git touches it`。

**风险**：阶段 3 将大规模搬迁文件，届时**某次检出可能重写整个文件的行尾符**，使 diff 被无关变更淹没，也让「仅改物理位置、不改内容」这一承诺难以自证。

**建议处置**：阶段 3 开始前引入 `.gitattributes`（`* text=auto eol=lf`）。

**需要你决定**：是否同意引入 `.gitattributes`，以及时点。

**决定**：引入，时点提前至阶段 1（见本节标题）。

## ☑ A9 · 冒烟基线曾隐性不确定：`/api/class-history` 的返回顺序 · **已决定：改 fixtures，不动业务代码**

> **决定（2026-10-01，授权范围内）**：改合成数据，**不改 `server.py`**。
> 理由见下方「为什么修在 fixtures 一侧」。业务代码零改动，生产影响零。

**时间**：2026-10-01 · **分支**：`refactor/phase-1-tests`
**位置**：`server.py:4854`（成因）、`tests_safe/fixtures.py`（处置）

### 现象

冒烟基线在整套运行时**约每 5 次失败 1 次**，单独跑或两两组合却总是通过。失败信息长这样：

```
"GET /api/class-history/2": {
  "recorded": { "length": 592, "digest": "8b3710d7d2617a14", "shape": {...} },
  "current":  { "length": 592, "digest": "35420ac76cf2b679", "shape": {...} }
}
```

**length 与 shape 完全一致，只有 digest 变**——这一点极具误导性：它看起来像"某条
字段的值变了"，实际上变的是**列表里两条记录的先后**。

### 成因（两条各修一半的缺陷叠加）

`server.py:4838` 的 `/api/class-history/{user_id}`：

```python
all_meetings = list(set(user_meetings + created_meetings))   # :4854
...
history.sort(key=lambda x: x["created_at"], reverse=True)    # :4902
```

1. `set` 对 ORM 实例按 `id()` 散列，**迭代顺序取决于对象的内存地址**，每次进程
   启动都可能不同；
2. `:4902` 按 `created_at` 排序，若两场课堂该值**相同**，这个 key 分不出先后，
   稳定排序便**保留列表原序**——也就是上面那个随机的顺序。

### 实测

`tests_safe/fixtures.py` 原本给两场课堂都写了 `created_at=BASE_TIME`，于是平局成立。
用独立进程各跑一次该路由，12 次结果：

```
8 次  [[2, ...], [1, ...]]
4 次  [[1, ...], [2, ...]]      （未改前）
```

修后同一探针 12 次**全部**为 `[[2, ...], [1, ...]]`。

### 为什么修在 fixtures 一侧，而不是 `server.py`

**真实的两场课堂不会同时同分同秒创建**——这个平局是合成数据自己造的。既然触发条件
由 fixtures 引入，就应当由 fixtures 消除。改 `server.py` 给排序加 `meeting_id` 次级键
虽然也能修好，但那是**为迁就测试数据去改业务代码**，与 C1 相悖。故：

- `fixtures.py`：第二场课堂改为 `created_at = BASE_TIME + timedelta(days=1)`
  （顺带贴合语义——进行中的课晚于已结束的课）
- 新增结构性守卫 `test_fixture_determinism.py::test_meeting_timestamps_are_distinct`，
  以「同表内不得有时间平局」的形式钉死这一类问题，而非只修这一处
- 基线因此重录；逐键比对确认**仅有 2 条路由变化**（`class-history/2`、`teacher-classes/1`），
  均为 `created_at` 取值改变的必然结果，无其它漂移
- 全量套件连续 25 次运行 **25 通过 / 0 失败**

### 遗留：同类隐患尚存（未处置，仅登记）

同仓另有 3 处 `list(set(...))`，其迭代顺序**取 PYTHONHASHSEED**（Python 默认每进程
随机化），同样不确定：

| 位置 | 所在路由 | 是否在基线内 |
|---|---|---|
| `server.py:1334` | `update_knowledge_graph()`（辅助函数） | 否 |
| `server.py:2501` | `POST /api/generate-report` | 否 |
| `server.py:4122` | `POST /api/generate-report-stream` | 否 |

三者均**不在冒烟基线内**，因此当前不产生失败；但将来若要为这三条路由补测试，会
撞上同一类问题。**未改动**——它们涉及报告生成链路，属排期在后的阶段 3/4。

**需要你决定**：是否接受「以 fixtures 修正 + 结构性守卫」这一处置；
是否同意把上述 3 处`list(set(...))`作为已知债留在阶段 3 处理。

## ☑ A13 · **一次对生产库的 DDL 尝试**，及收集闸门的缺口 · **已修复；有一项需你授权核验**

**时间**：2026-10-01 · **分支**：`refactor/phase-3-structure`

> 这是本次重构中**唯一一次触碰生产环境风险的事件**，按你「警惕对生产环境的直接操作」
> 的要求单独立条、如实记录，不作淡化。

### 事实

归档第三组（`tests/`、`test/`、根级 `test_*.py`）后，我在验证归档闸门时执行了：

```bash
pytest archive/legacy-tests/tests-dir/test_api_endpoints.py --collect-only
```

**结果**：`3 tests collected in 3.59s`。

这 3.59 秒是一次真实的 **`import server` → `import database`**。而
`database.py:243` 的 `_ensure_transcripts_columns()` 在**模块导入期**运行，
列缺失时会对 `DATABASE_URL` 执行 `ALTER TABLE transcripts ADD ...`——
工作区的 `.env` 指向生产阿里云 RDS。**即：一次对生产库的 DDL 尝试。**

### 为什么闸门没拦住

当时以为有三道防线，**实际只有一道半**：

| 防线 | 实际情况 |
|---|---|
| `pytest.ini` 的 `testpaths = tests_safe` | ❌ **显式路径参数会完全覆盖它** |

根因是一条反直觉的 pytest 语义：**显式给出的参数被登记为 *init path*，
pytest 有意豁免它们的一切 ignore 检查**（"用户明确点名要跑的东西，不要偷偷跳过"）。

我随后又试了 `pytest_ignore_collect`——它看起来是"每个待收集路径都会经过"的钩子，
**实测同样无效**，原因相同。两种做法都作为否定结论写进了
`archive/legacy-tests/conftest.py` 的文件头，以免后来者重试。

1. **仓库根 `conftest.py`（新增）**——把隔离移到**任何调用方式下都会加载**的位置。

   有效的形态。

3. **测试头部打印隔离状态**（`pytest_report_header`）——隔离失效时**不会有任何
   症状**，所以把当前生效的目标显式印出来，失效时至少看得见。

### 实测二：`ASRSessionManager` **不是**一个可以机械搬迁的叶子模块

设计文档 §4.1 把它与 `connection.py` / `signaling.py` 并列，看起来是同一种搬迁。
实测（AST 求自由变量）之后不是：

```
ASRSessionManager                759 行
 ├─ 依赖 3 个 server.py 内部函数（1490+ 行）
 │    _create_realtime_transcript_entry           144 行
 │    _run_realtime_speech_analysis               168 行
 │    _stream_realtime_speech_analysis_events      64 行
 ├─ 而这 3 个函数又依赖另外 8 个 server.py 内部名字：

 │    update_knowledge_graph / AIInsight
 └─ 还依赖 3 个**共享单例**：kg_service / kg_counter / llm
      ——它们被大量其他端点使用，不能随本模块搬走
```

`connection.py` / `signaling.py` 能干净搬走，是因为它们是**自包含叶子**——
实测 98/98 与 21/21 行逐字相同，改的只有 import 头。
`ASRSessionManager` 不是，它牵出 **11 个函数、约 1500 行、3 个共享单例**。

**构成循环导入**。绕开的唯一办法是先把 `services/` 层建起来。

### 结论：阶段 3 应拆成两件事，且顺序相反

原计划是「自顶向下按 §4.1 目录搬」。实测表明必须先**自底向上把层建出来**，
否则每一次搬迁都会拖出循环依赖：

| 步骤 | 内容 | 风险 | 可验证性 |
|---|---|---|---|
| **3.1** | `app/models/`——从 `database.py` 拆出 ORM 模型 | 低（叶子） | 高：`database.py` 覆盖 93% |
| **3.2** | `app/core/`——`config.py`、`database.py` 迁入 | 低 | 高（74% / 93%） |
| **3.3** | `app/services/`——`llm` / `kg_service` / `kg_counter` 等共享单例抽出 | 中 | 低（18% / 18%） |
| **3.4** | `app/repositories/`——数据访问 | 中 | 低 |
| **3.5** | `app/realtime/asr_session.py`——此时依赖已就位 | 中 | 极低（6.1%） |
| **3.6** | `app/routers/*`——13 个业务域路由 | **高** | 低（8.8%） |
| **3.7** | `app/main.py` 装配；`server.py` 退化为兼容外壳 | 中 | 中（路由契约 64 条） |

**3.1–3.2 现在是可做的**（覆盖率高、是叶子），**3.5–3.6 不是**。

### 一个覆盖率之外的办法：逐字等价证明

`connection.py` / `signaling.py` 那次搬迁，我用的是**与覆盖率无关**的验证法：

1. 搬迁后的文本与原文**逐行比对**，差异只允许出现在 import 头；
2. 每个自由名在新模块中解析到的**对象**与在 `server.py` 中解析到的**是同一个**。

若两条都成立，则行为按构造保持不变——**不需要测试覆盖**。这也是为什么那两个模块
敢在 0% 覆盖下搬迁。

**这个办法对 3.1–3.4 同样适用，对 3.6（路由拆分）很难适用**：路由拆分要把
函数体从装饰器下摘出来、换依赖注入方式，文本必然大改，等价证明不成立。
**3.6 是真正的"重构"而非"搬迁"，风险性质不同。**

### 顺序：先立守卫，再动搬迁（这是本步最重要的决定）

搬迁会留下一种**只在生产上发作**的错误：调用点还写着旧名字 `from ai_core import ...`。
它不制造错误结果，只抛 `ModuleNotFoundError`——但发作时机很坏：

- `server.py:3410` 的 `from ai_core import RealtimeTranscriber` 在**处理器函数内部**；
- `server.py:152` 的 `from video_processor import ...` 在 `get_analyzer()` 里；
- `app/services/video_processor.py` 里还有更靠后的一层（连本地 Ollama 时才用到）。

这些路径测试走不到，所以**漏改的话全套测试依然全绿**，线上第一个用该功能的
用户拿 500。因此第一步不是搬，而是写一条**按 AST 扫全仓库**的守卫
（`tests_safe/test_module_moves.py`），此后每搬一组就登记一组。

守卫的价值不在"通过"，在**它把改动面穷举了出来**：把 11 个待搬模块临时登记后
重跑，**22 处调用点一处不漏地被列出**（含两处延迟导入的 `ai_core`）。
换言之后面每一步改哪些行是算出来的，不是靠 grep 碰运气的。

守卫本身也按本仓库的老规矩立了三道：
1. 注册表路径必须真实（旧的已不存在、新的确实在）——否则它退化成"没在检查"；
2. 检测函数有**阳性 + 阴性对照**——否则它内部写坏了也照样显示"仓库干净"；
3. 失败信息直接写出正确写法。

### 三个"静默降级点"，按危险性排序

搬错名字时，三处的后果差别很大，值得你知道：

| 位置 | 失败后的行为 | 危险度 |
|---|---|---|
| `server.py:104` OSS | 被 `except Exception` 吞掉 → `USE_OSS = False`，只打印一行 "OSS not configured" | **最高**：应用照常启动，对象存储静默不可用，那行日志淹没在启动噪声里 |
| `server.py:3410` / `:152` 延迟导入 | 真抛错，但只在对应功能被使用时 | 中：测试绿、线上崩，排查时现场离原因很远 |
| `server.py:112` `ai_core` | `except ImportError: sys.exit(1)` | 低：够吵，立刻被发现 |

三者现均由守卫静态覆盖，不依赖人记得。

## ☑ A20 · A19 答错了问题：`server.py` 该**拆**，而不是"搬不搬" · **已获你批准，执行中**（进度见 A22）

**时间**：2026-10-01 · **分支**：`refactor/phase-5-server-decomposition`

### 我承认的问题

你在问：「server 为什么行数这么多？后端重构不就是为了提高可维护性，为什么这么大还不能拆？」

A19 论证的是**搬**（relocation）——把整个文件从根目录挪进 `app/`。我把它当成
"server.py 该怎么办"的全部，于是得出了"不搬，它没问题"的结论。
但你问的是**拆**（decomposition）——把一个文件按业务域切成多个。
这是两件不同的事，而**拆**才是"提高可维护性"的正解。

A19 里"代价与收益不成比例"这句，对**搬**是对的，被误读成对**拆**也成立则是错的。
这是我的表述造成的，责任在我。

### 为什么它这么大（实测，非估计）

| 项 | 数量 |
|---|---|
| 总行数 | 6470 |
| 有效行（非空非注释） | 5284 |
| 路由处理器函数体合计 | **约 3350 行** |
| 顶层函数 | 100 |
| 顶层类 | 1（`ASRSessionManager`，**759 行**） |

最长的几个处理器：`generate_learning_report` 222、`generate_report_stream` 215、
`get_emotion_details` 215、`login` 165、`get_realtime_stats` 163。

`/api/emotion-details/...`、`/api/teacher-stats/...` 等等。也就是说大部分路由是
"一条路一个功能"，**天然可切**。这不是一坨盘根错节的意大利面，而是大量独立单元
被塞进同一个文件。

### 为什么"拆"比"搬"难得多（真实障碍，不是推脱）

1. **可证性从"逐字节"掉到"行为契约"。** 阶段 3 的搬迁能拿逐字节比对证明零改动

   名字空间。这正是 A15 定案"搬迁与重构必须分开对待"要防的情形。

2. **约 30 个模块级可变全局量被 59 条路由共享**：`analyzer`、`kg_counter`、
   `recent_speech_cache`、`recent_media_state`、`REALTIME_*`、
   `ASR_SELF_VOICE_GATE_*`，以及三个单例 `manager` / `signal_manager` /
   `asr_manager`。每一个都要决定"搬走还是留下"，**决定错了是静默行为变化**。

3. **`manager` / `ConnectionManager` 是对外可见的。** `tests_safe/test_websocket_and_manager.py`
   从 `server` 导入它们；`server.py:2723` 的注释写明单例身份必须由 `server` 模块持有，
   拆掉边界会让不同调用点拿到不同对象——而且完全静默。

4. **导入期副作用**：`import app.core.database` 本身即可能做 DDL；server.py 导入时
   建目录、挂 `mount("/storage")`、改 `sys.path`。拆开后"何时执行什么"要重排。

### 为什么现在可以动手：安全网已经在了（阶段 3 的副产品）

| 测试 | 钉住什么 |
|---|---|
| `test_route_contract.py` | **59 条路由的地址+方法**，改一个字符即红 |
| `test_route_baseline.py` | 只读路由的响应状态码/长度/结构摘要 |
| `test_websocket_and_manager.py` | 单例身份 |
| `test_paths_anchor.py` | 搬运后锚点不漂移 |

**这正是"拆"能安全进行的前提：不需要相信自己没改坏，只需要让测试证明。**

### 拟定方案（按业务域切，一次一组 → 一组一次契约测试）

用 `APIRouter`，**按业务域**而非 URL 前缀切（前缀是巧合，会切出无意义的模块）。

### 三个值得记的决定

**1. 容器默认连不上生产库，而且是靠既有语义做的。**
`app/core/config.py::_apply_env_file` 用 `os.environ.setdefault`——
**进程里已有的环境变量赢过 `.env`**。这条既有语义正好当安全阀：
compose 的 `environment:` 显式给出那 6 个数据库键，`.env` 里指向生产 RDS 的
同名值就再也盖不过来。容器里实测 `engine = sqlite:///./storage/app.db`。

为什么较真：`app/core/database.py` 的 `_ensure_transcripts_columns()`
**在导入期执行**（"import 即 DDL"，见 A13）。容器起来连哪个库，
直接决定它会不会对生产库发 `ALTER TABLE`。

**刻意不提供**"连生产库"的现成叠加文件——那等于把危险变成一个随手可及的开关。
要用的话得自己写那份叠加文件，步骤写在 `deploy/docker.md`。

**2. 依赖切分从 `requirements.txt` 现算，不另立清单。**
在 Linux 上 `pip install torch` 默认拉 CUDA 版——镜像凭空涨好几 GB。
（Windows 上恰好默认是 CPU 版，**所以这个问题在开发机的 venv 里根本看不见**，
只有容器里才暴露。）修法是 torch 三件套单独走 `pytorch.org/whl/cpu`。
但"哪三个包算重"这份知识若抄进 Dockerfile 就有了两处定义——本仓库吃过太多次
这个亏（`app/core/oss.py` 文件头）。所以由工具现算，并断言它声明的每个包
都真的在清单里。实测装到的是 `torch 2.14.1+cpu`，`cuda None`。

**3. `.dockerignore` 第一条就是 `.env`。**
`Dockerfile` 最后一步是 `COPY . .`，漏掉就是**生产口令打进镜像层**——
而镜像层只增不减，事后改 `.dockerignore` 也抹不掉。有断言钉住。

| 行 | 键 | 该行 `{` 处的深度 |
|---|---|---|
| 5279 | `el` | 1 |
| 5280 | `data` | 2 |
| 5533 | `computed` | 2 |
| 5730 | `watch` | 2 |
| 5780 | `methods` | 2 |
| 11260 | `beforeDestroy` | 2 |
| 11287 | `watch` | 2 |

（`el` 那行没有 `{`，所以报 1；其余 `xxx: {` 在 `{` 处已是 2，即**键本身同在深度 1**。）
7 个键里 `watch` 出现两次，且都在这一个对象字面量里 —— **是兄弟键，不是嵌套**。

JavaScript 对象字面量对重复键的语义是**后者整体胜出**：不合并、不警告
（非严格模式静默，而 `<script>` 里这段也不是模块）。所以真正生效的只有
11287–11295 那个 `watch`（`showKnowledgeGraph` 一个监视器）；
5730–5779 那个（`localMediaStream`、`onlineMembers`、`classroomTab` 三个监视器，
