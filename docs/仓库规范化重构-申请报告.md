# 智能协作学习系统 · 仓库规范化重构计划


---

## 摘要

本系统仓库缺乏规范化管理。经过对代码、配置、依赖与测试资产的逐项核查，确认当前存在 **四类已经在真实环境中暴露过的问题**：

1. **环境不可复现**——服务已因依赖问题无法启动过；
2. **配置错误会静默生效**——服务可能"看起来完全正常"却在读写错误的数据源；
3. **测试资产存在但无法运行，且一旦运行会污染生产数据**；
4. **代码、文档与线上实现三者脱节**

本次重构的目标是：**在不改变业务逻辑、不删除任何代码、不中断线上服务的前提下**，重新组织仓库结构，隔离开发与生产环境，并建立可验证的质量基线。

计划分为 8 个阶段

---

## 一、现状与已暴露的问题

本节所有结论均来自对仓库的直接核查与实测复现，不含主观判断。

### 1.1 环境不可复现——已导致服务无法启动

- 仓库内自带的 `venv/` 目录是在**另一台机器**上创建的（其配置指向 `C:\Users\20474\anaconda3\`，该路径在本机不存在）。其中所有可执行文件均已失效，直接使用会报"找不到可执行文件"。
- 按文档在本机重建环境时，`setuptools` 自动升级至 84 版，移除了 `resemblyzer` 依赖链所必需的 `pkg_resources` 模块，**导致服务无法启动**。
- 根本原因：`requirements.txt` 共 **40 项依赖，其中仅 1 项有版本约束**。上述故障会在**每一次**环境重建时重复发生。

**业务影响**：更换开发机器、新增开发人员、或部署到新服务器时，服务均可能无法启动，且排查需要数小时。

### 1.2 配置错误会静默生效——服务可能"看起来正常"却连错数据源

这是本报告中**最需要引起重视**的一条，因为它不产生任何报错、日志或告警。

系统通过 `config.py` 定位配置文件 `.env`，并从中读取数据库地址。**实测复现**：将该文件移动到子目录（这是重构中必然发生的操作），配置文件定位基准随之改变；当 `.env` 在最末位置找不到时，程序**静默跳过加载**，回退到默认值 `sqlite:///./storage/app.db`。

**实际后果**：服务正常启动、页面正常打开、所有功能表面上可用，但实际读写的是一个**空的本地文件数据库**，而非线上数据库。该问题**无任何报错提示**。

同类问题另有一处：服务有 **13 处**使用"当前工作目录"来定位数据目录。从其他目录启动服务，会在错误位置创建一套空目录，历史音视频与报告数据全部读不到——同样不报错。

**业务影响**：数据错位可能长期不被发现；一旦发生，历史数据与用户数据的一致性难以恢复。

### 1.3 测试资产存在但不能运行，且一旦运行会污染生产数据

仓库中实际存在约 **70 个测试函数**（`tests/` 目录下 59 个为 pytest 用例，另有一套自建回归测试框架）。这些资产**不能作为质量保障使用**：

- **无法运行**：`pytest` 未安装、未在依赖清单中声明，也没有任何测试配置文件。该套件**当前跑不起来**。
- **会污染生产数据**：测试中有 **38 处直接发起写操作**，而测试读取的数据库配置指向**线上生产库**。例如 `test_llm_endpoints.py` 会向 `/api/save-transcript` 提交一条伪造的会议转录记录（`meeting_id:1, user_id:1`）——**一旦运行，将真实写入生产数据库**。
- **断言形同虚设**：断言普遍过弱，如 `assert status_code in [200,400,422]`、`assert len(data) > 0`，个别用例甚至为 `assert True`。其中一条用例在缺失必填字段的请求上断言成功，**必然失败**——说明该套件**从未通过过**。

**业务影响**：项目实际上处于**无质量保障**状态；而现有的"测试"又构成一个随时可能被误触的数据风险。

### 1.4 代码、文档与线上实现三者脱节

- `DEPLOYMENT.md`（约 1200 行）内容**完整重复了两遍**，且描述的部署方式（MySQL、pymysql、3308 端口）与线上实际实现（SQL Server、pymssql、3433 端口）**完全不符**。按该文档部署无法得到可用系统。
- 顶层 57 个 Python 模块中，**仅 15 个与线上服务运行直接相关**，其余 42 个为历史遗留，包括：
  - 一次性代码修改脚本（`remove_all_emojis.py`、`update_backend.py`、`modify_backend.py`、`temp_fix.py` 等）——执行完毕后即失去意义；
  - 手工检查与调试脚本（`check_*.py`、`debug_emotion_data.py`、`diagnose_agora.py` 等）；
  - 一整套**从未接入主服务**的声纹识别模块（`voiceprint_api.py`、`speaker_diarizer.py` 等 8 个文件）。
- 业务代码本身也留有大量"临时维持链路"的痕迹，例如源码中标注"临时禁用声纹门控，允许所有用户语音转文字"的硬编码开关。

**业务影响**：新人无法从仓库判断哪些是有效实现；维护时必须通读全部代码才能确认改动安全性，维护成本随规模持续上升。

## 二、重构作用

### 2.1 降低线上故障概率

上述 1.1 与 1.2 两类问题**已经发生过**，且会在每次换机器、重装环境、或调整目录结构时**重复发生**。1.2 类问题尤其危险——它不报错，可能造成长期的数据错位。规范化重构直接消除这两类故障的成因。

### 2.2 建立可验证的质量保障

在重构**之前**先建立测试基线，使"不影响业务逻辑"从一句承诺变成**可被自动验证的事实**：每一次代码搬迁后运行测试，行为一致才允许继续。这既是本次重构的安全网，也是项目后续长期的质量基础。

### 2.3 使生产部署可复制

当前部署依赖约 317 行的手工脚本、systemd 配置与 nginx 手工配置，且脚本已与实现脱节。重构后可通过一条命令在任意服务器复现环境，显著降低部署与迁移成本。

### 2.4 消除敏感信息暴露风险

当前生产环境的数据库口令、多组云服务密钥、大模型 API Key 均以**明文**形式存放于项目目录下的配置文件中。

说明：经核查，该配置文件**未被纳入版本控制**（已在忽略清单中，历史记录中亦从未出现），因此**不存在已泄漏至版本历史的情况**，无需紧急处置。但任何取得项目目录的人即可直接获得生产数据库的完整访问凭据；通过压缩包、共享目录或拷贝等方式交接时，凭据会一并扩散。重构将把密钥与代码彻底分离，并明确开发与生产两套配置的边界。

### 2.5 降低后续维护与交接成本

明确划分"线上有效代码"与"历史留存代码"的物理边界，使新成员能够快速建立正确认知，也使每次改动的影响范围可被准确评估。

## 三、影响评估

### 3.1 明确不受影响的部分（承诺）

本次重构遵循以下**硬性约束**，并接受逐项验收：

| 项目 | 承诺 |
|---|---|
| **业务逻辑** | 不做任何功能性修改 |
| **功能完整性** | 全量保留所有代码，**不删除任何文件**；非线上有效代码仅做物理位置搬迁 |
| **数据库** | 不改动任何表结构与数据 |
| **对外接口** | 59 个接口的地址、入参、出参保持不变 |
| **前端行为** | 页面功能与交互保持一致 |
| **线上服务** | 重构过程中不中断线上服务，不引入停机窗口 |

### 3.2 会发生的变化

| 变化项 | 说明 | 可逆性 |
|---|---|---|
| 文件物理位置 | 模块归入相应目录 | 完全可逆 |
| 代码组织方式 | 单文件按职责拆分 | 完全可逆 |
| 依赖版本 | 从未约束改为**锁定版本**，锁定的目标为**线上正在运行的版本** | 完全可逆 |
| 配置读取方式 | 由明文集中文件改为分环境配置 | 完全可逆 |
| 构建与启动方式 | 引入容器化与前端构建流程 | 完全可逆（旧方式保留） |

### 3.3 主要风险与缓解措施

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| 重构改变行为且未被发现 | 中 | 高 | **阶段 1 先行建立测试基线**，之后每次改动均自动验证；每阶段独立验收 |
| 路径调整引发 1.2 类静默错误 | **高** | 高 | **阶段 0 最先修复路径锚点**，并加入自动校验，确保数据源指向可被断言 |

## 四、实施计划

### 4.1 阶段划分

| 阶段 | 内容 | 主要产出 | 验收标准 |
|:---:|---|---|---|---|
| **0** | 路径锚点统一 + 冒烟基线 | 统一的项目根定位机制；全部接口的基线响应记录 | 从任意目录启动均指向同一数据源；基线可稳定复现 |
| **1** | 测试体系建立 | 可运行的测试框架；生产库隔离机制；行为快照基线 | 一条命令跑通全部测试；**确认不存在任何写入生产库的路径** |
| **2** | 依赖版本固化 | 锁定版本的依赖清单 | 全新环境可一次性复现启动 |
| **3** | 后端结构重构 | 按主流框架惯例分层的目录结构 | 阶段 1 测试全部通过；接口契约不变 |
| **4** | 配置改造 | 分环境配置体系；密钥与代码分离 | 密钥不再出现于仓库；切换环境无需改代码 |
| **5** | 容器化 | 开发与生产两套镜像及编排配置 | 一条命令启动本地环境；远程部署可复现 |
| **6** | 前端工程化 | 构建流程接入；外部依赖本地化 | 构建产物与现网行为逐项一致 |
| **7** | 前端组件拆分 | 按职责拆分的组件结构 | 功能逐项对照通过 |
|  |  | **合计** | **30–55** |

### 4.2 关于工期的说明

- **阶段 0–2（约 5–8 人日）**：范围小、边界清晰，估算可靠。**这三阶段完成后，重构的安全性即已建立**——后续工作即便暂停，项目也已获得实质改善。
- **阶段 3–7**：涉及大规模代码搬迁，估算区间较宽。**将在阶段 1 完成后，基于实测的测试覆盖率与代码依赖关系重新精算**，并提交修订后的计划供再次确认。
- 上述估算基于单人投入。可并行的部分（如阶段 4 与阶段 6）可视人员情况压缩总工期。

### 4.3 推进顺序的理由

- **阶段 0 必须最先**：不统一路径锚点，任何文件移动都可能在触发 1.2 类静默错误。
- **阶段 1 必须先于阶段 3**：测试基线是"不影响业务逻辑"这一承诺的唯一客观证据。
- **容器化（阶段 5）刻意靠后**：其价值在环境稳定后才兑现；若与代码搬迁同时进行，一旦出问题将无法区分成因。同时避免在重构早期引入较大的镜像下载成本。
- **依赖管理工具的更换不列入本次计划**：当前仅需"锁定版本"这一项实际收益，用现有工具即可达成，无需引入新工具链。
- **前端拆分（阶段 7）最后进行**：前端单文件逾 11000 行，改动面最大、自动化验证成本最高，应在后端稳定、测试体系成熟后启动。

## 六、验收与回退

### 6.1 阶段验收

每个阶段完成后提交简要报告，内容包括：完成事项、验证结果、遗留问题。**未通过验收不进入下一阶段。**

### 6.2 回退机制

- 全部改动在独立分支进行，与现有线上版本完全隔离；
- 每个阶段为独立提交，可单独回退而不影响其他阶段；
- 重构期间不修改生产环境，线上服务不受影响。

### 6.3 最终验收标准

1. 全部测试通过，且确认测试过程**不触碰生产数据**；
2. 从任意目录、任意机器可一次性复现完整运行环境；
3. 生产密钥不再出现于仓库中；
4. 59 个对外接口的输入输出与重构前**完全一致**；
5. 重启后可复现此前故障场景而不出现数据错位。

## 附录 B：术语对照

| 术语 | 通俗解释 |
|---|---|
| 仓库（Repository） | 存放项目全部代码与历史记录的目录 |
| 依赖 / 依赖清单 | 项目运行所必需的外部软件包及其清单文件 |
| 版本约束 | 指定外部软件包使用哪个具体版本；缺少约束时软件会自动升级到最新版，可能引入不兼容故障 |
| 静默失败 | 程序出错但不报错、不提示，继续"正常运行"，导致问题长期不被发现 |
| 测试基线 | 在改动前记录系统的现有行为，改动后对比，用以证明行为未被改变 |
| 容器化 | 将运行环境（操作系统、软件、配置）整体打包，使其可在任意机器上一致复现 |
| 分层重构 | 按职责把代码拆分到不同目录，而不改变代码本身的功能 |
| 回退 | 撤销某次改动，恢复到改动前的状态 |
